## Operating policy

1. **New PRs are ALLOWED immediately.** Create a reviewable PR per coherent feature or fix, preferably an end-to-end vertical slice. Use draft PRs for active work; never call a draft done. No blanket ban on opening issues or PRs, but do not create paperwork to replace implementation.
2. **Queue discipline:** aim for **3 active development PRs** at a time, with an upper working limit of **5** pending active review/integration; exclude #352/#367 from this capacity because they are separately owner-gated publishing holds. If more work is independent and justified, explicitly coordinate/reconcile before exceeding that limit; **do not let opened PRs grow without an integration owner or next action**. Prefer an engineer completing/merging a ready PR to starting a sixth.
3. **Merge continuously after appropriate review:** check exact current `main`, rebase/retarget stale branches, relevant current-head CI and focused regression/permission tests, then merge ready nonpublishing PRs promptly in small coherent waves. Respect existing branch protection, security checks, review ownership and appropriate integration/device QA. Don't block an unrelated tested feature waiting for a huge backlog-wide audit or for website publication.
4. **Subagents:** main Codex is the integrator; use 2–4 bounded independent subagents when complexity warrants, with named task, owned file/domain and a concrete handoff. Prevent collisions in Tauri host ACL, shared schemas, scene state, Prepare/Live shell, translations and native recorder. Integrate/test/reconcile delivered branches rather than leaving dozens of stale agent PRs.
5. **Priority:** owner fixes first; complete significant approved workflows **Prepare → Design/Library → Live → actual receiver outputs → Comms/roles → Rhema native selected congregation-output recording → History**, then device/OBS/Cam/TV/Companion and bilingual acceptance. Advance unrelated lanes concurrently where safe. Use [46 — 11-page operator acceptance register](rhema-studio/46-operator-pages-owner-approval-and-implementation-register.md) and [32 — feature coverage](rhema-studio/32-feature-coverage-inventory.md) to avoid missing features. Reuse working code; do not rebuild what was merged.
6. **Tests:** run **focused tests during development** and required current-head safety/host authorization/build checks before merge. May optimize redundant tests/CI to keep iteration fast, but **do not bypass security-critical, output Take, recording/data-integrity, role-scoping or branch-protection gates**. If hardware is unavailable, report its acceptance as pending, not passed.
7. **Hard holds:** **DO NOT MERGE, DEPLOY, PUBLISH, REBASE INTO MAIN VIA ALTERNATE ROUTE OR OTHERWISE ACTIVATE WEBSITE PUBLICATION CHANGES FROM PR #352 OR #367** without explicit fresh owner approval. This hold applies to their content, not merely their PR numbers. Do not use a new PR or direct-main commit to circumvent it. No unapproved application release, actual church/live service changes, production migrations, external provider actions or security-policy exceptions.
8. **Visibility:** maintain a small current task/PR board: `ACTIVE`, `IN REVIEW`, `BLOCKED`, `MERGED / VERIFIED`, `OWNER-GATED`. Report `main SHA`, open development PR count vs owner-gated PR count, merged feature/fix, tests actually run, exact subagent handoffs and next actionable integration. PR creation, green CI, merge and real-device acceptance are distinct facts.
