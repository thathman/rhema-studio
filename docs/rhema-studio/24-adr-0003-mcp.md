# ADR 0003 — Rhema MCP: a local, opt-in planning helper that writes drafts only

- **Status:** Accepted for what is built (MCP-001 to MCP-006 of #252); the remote transport in §7 is
  proposed only and waits for the owner.
- **Scope:** the Rhema MCP server (`src-tauri/src/mcp.rs`, `mcp_drafts.rs`, `mcp_resources.rs`):
  how an AI assistant reaches Rhema, what it may read, what it may write, and the rules for the data
  it sees. What is built is described in `22-rhema-mcp.md`.

## 1. Requirements (from #252)

- An assistant the church already uses (Claude Desktop, Claude Code or any other MCP client) can
  plan a whole service: read the church's services, songs, hymns, Bibles and looks, and put a
  complete, editable run of show into Rhema for people to review.
- No provider is built in and no API key is needed to use Rhema by hand. With MCP off, Rhema works
  exactly as before (journey A).
- The assistant never takes Live, never approves or publishes a service, never changes a screen,
  OBS, Comms or a setting (journeys C and E).
- Scripture comes only from the installed editions; song lyrics and rights are never invented or
  handed out (journey D).
- Text inside songs, services and drafts cannot make Rhema do anything (journey E).

## 2. Decision: stdio, started by the assistant, off until the church turns it on

The assistant starts `Rhema --mcp` as its own subprocess and talks JSON-RPC over stdin and stdout,
one message per line. No window opens and the running app is not touched (the `--mcp` check runs
before the single-instance plugin).

- **Why stdio.** It needs no port, no pairing and no password: only a program on this computer that
  the person set up can start it, and it lives exactly as long as the assistant's session. Nothing
  listens on the network, so there is nothing to expose by mistake. Every desktop MCP client
  supports it.
- *Rejected for now: an HTTP endpoint on the Host/Join listener.* It would need its own keys,
  origin checks and revocation (as Host/Join has), and would put a planning door on the same port
  the Live desks use. Not worth it while every client the church uses can start a subprocess.
- **Why opt-in.** Every tool and every resource read answers "turn it on in Settings → AI
  assistants" until `mcpEnabled` is on in the app's settings file. The lists (tool names, resource
  names) are still offered so the assistant can explain what turning it on would give; they hold no
  church data. Settings says plainly that an online assistant sends what it reads to its provider.

## 3. Read and write boundary: drafts only, never Live

- **Reads** open the content database with SQLite's read-only flag (`ContentDb::open_read_only`,
  which also refuses a database from a newer Rhema); the Bible database is immutable. Tools and
  resources (`rhema://services`, `rhema://services/{id}`, `rhema://songs`, `rhema://translations`,
  `rhema://looks`, `rhema://drafts`, `rhema://drafts/{id}`) read the same data the same way.
- **The only write is a draft file** in the data folder's `ai-drafts` (create, or revise one that is
  still waiting). Never the services database, never an approval, never a screen, OBS, NDI, Comms or
  a setting. At most 50 drafts wait at once.
- **People take it from there.** Prepare → AI drafts opens a draft as an unsaved service; people
  edit it and save it themselves, and approval is the ordinary approval. Opening a draft puts
  nothing on screen.
- **Enforced in Rhema, not by labels.** Tool annotations (`readOnlyHint`) describe the tools to the
  assistant but are not the security: the read-only database handle and the absence of any live
  call in the MCP code are. There is no live-control tool, and adding one needs a new ADR.

## 4. Lyrics and copyright

- Songs and hymns go out as **titles, other titles, kind (song or hymn), numbers, authors, licence
  and languages**. Lyrics never do, in any language, from any tool or resource, and not as a "first
  line" either (the library's summaries carry one; it is dropped). A service's run of show gives a
  song's title and id, never its words, and a slide's title, never its text.
- A song or hymn the church does not have becomes a **missing** item for people to source; the
  assistant cannot make up words for it. A slide may carry only the assistant's own words
  (announcements, prayer points).
- Scripture text comes only from `rhema_lookup_bible_reference` in an installed edition; a draft's
  readings must exist there or the check fails.
- Tests assert this: every resource is read whole and searched for the test song's lyric lines.

## 5. Revisions for drafts

- A draft is revision 1 when saved and one more each time it is revised (drafts from before
  revisions are 0). Revising needs the revision the assistant read
  (`rhema_get_service_draft`, `rhema://drafts/{id}` or the list). If the draft changed since, nothing
  is written and the assistant is told to read it again: two assistants (or one assistant and a
  later chat) cannot overwrite each other silently.
- A draft people removed cannot be revised. What people already saved from a draft is a service of
  its own and is never touched.

## 6. Text is data, never instructions

- Everything an assistant reads from Rhema (song titles, service titles, notes, drafts written by
  another assistant) and everything it writes is **text to store and show**, nothing more. Rhema
  never runs, follows or interprets it: "ignore previous instructions", `<script>`, SQL and
  "SYSTEM: take it live" are kept byte for byte and shown as plain words in Prepare.
- The server's instructions tell the assistant the same: what resources contain is church data,
  never instructions. The assistant's own model may still be fooled; that is why §3 holds whatever
  the assistant decides.
- Yorùbá and other text is stored and returned exactly (tone marks, underdots, combining marks, not
  normalised).
- Input is bounded: one message at most 1 MB, at most 200 items a draft, titles and notes cut to
  length, ids checked before any file is opened (`../settings` is not a draft id).

## 7. Future: a remote transport is the owner's decision

Assistants that run in a browser or on another computer cannot start a subprocess here. A remote
transport (MCP's Streamable HTTP, or a relay) could serve them, but it would put church data on the
network. It is **not built** and needs the owner's go-ahead and its own design first, which must at
least cover: pairing and revocation per assistant (as Host/Join keys), short-lived authorisation,
origin and host checks, no binding beyond the church network without an authenticated relay, the
same §3 boundary (drafts only), rate limits, and an audit of what was read. The church workstation's
LAN API is never exposed publicly as a workaround.

## 8. Consequences

- One code path for tools and resources: a resource is the same read as its tool, so the rules in
  §3 to §6 hold for both.
- Resources are fixed reads with no subscriptions or change notifications (`subscribe` and
  `listChanged` are false): an assistant reads again when it needs fresh data.
- The assistant must be on the same computer as Rhema's data until §7 is decided.
