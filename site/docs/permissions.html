HOST-CONTROLLED ACCESS

Permissions & access

The main host assigns roles and limits connected desks to the actions and outputs they need.

Implementation status: the desktop Permissions workspace, paired-device role controls, selected output scopes, a separate Recorder grant, and saved scene-change requests exist in the repository. Complete browser workspaces for every role and the wider approval-request system are still in development. A visible control does not prove every role/device workflow has been accepted.

Who decides access?

The Rhema host is the authority for its paired devices. The host pairs a device, assigns or changes its role, limits the outputs it can affect where applicable, and can pause or revoke its control. The host checks protected commands; changing a browser screen or local setting cannot grant additional access.

A paired device without an explicit role is treated as Viewer. Viewer access is read-only for production changes. Comms functions that are available to all paired team members follow their own host rules.

Roles in the current access model

Role names describe host-authorized responsibilities. They do not mean that a finished browser page exists for every role.

  • Presenter: host-approved service presentation and production controls.
  • Configure: additional host setup, scene, and configuration controls under the command policy. Recorder access is still a separate grant.
  • Bible: Scripture preview and the Bible actions allowed by host policy.
  • Worship: song and hymn preview or presentation actions allowed by host policy.
  • Screens: scene actions only for assigned outputs. Group Take has a separate grant and requires reviewing the selected target outputs.
  • Timekeeper: permitted event and timer controls.
  • Stage: private Stage messages within host-assigned Stage recipient policy.
  • Camera: camera-related scene visibility and actions available under host policy.
  • OBS Director: controls for OBS's own Preview, Program, stream, and recording; this does not control Rhema's congregation outputs.
  • OBS Companion: a separate connected tool for OBS on another computer.
  • Editor: permitted service and scene editing actions.
  • Viewer: read-only access to permitted show information.

For task-specific responsibilities and current limits, use the operator overview and individual operator guides.

Output and action scopes

  • A Screens role does not automatically include every screen. The host must assign the output IDs that desk can control.
  • Group Take is separate from a single-output Take and remains denied until the host grants it for the relevant outputs.
  • Approval of a saved scene-change request does not itself Take that scene live.
  • Rhema's native recorder is separate from OBS recording and from every role. A paired desk can control it only when the host gives that device the explicit Recorder grant.
  • Private Stage information and operator Preview must stay out of congregation and OBS outputs unless a distinct, authorized action places appropriate content there.

Pairing and revocation

  1. The main host opens pairing and shares the temporary pairing instructions with the intended desk on the trusted local network.
  2. The host identifies the paired device, chooses its role, and assigns any required output scope or separate grant.
  3. The host can pause or revoke a device. Existing connections do not make the device a host or allow it to change its own access.
  4. Keep pairing codes, QR images, keys, certificate details, and private host addresses out of public screenshots and messages.

The current complete browser operator application is not ready to claim. See Connected operators & LAN browser access for what runs in the browser and what remains in development.

Requests and approvals

The desktop Permissions workspace includes saved scene-change requests. Accepting one authorizes that scene change under host policy; it does not publish the scene. Other proposed requests, such as expanded role grants or a broad approval inbox for all operator actions, remain in development until their typed host-side behavior and review history are complete.

Read the repository's Permissions and authority design for the approved direction and host permission contract for current server-side checks.
